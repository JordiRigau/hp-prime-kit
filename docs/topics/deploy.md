# Getting it onto the calculator

Facts about the two destinations -- the emulator and a physical calculator --
rather than about one command. Each has an identifier, says how it is known,
and is stated here once.

They do not work the same way. The emulator has a folder you can write into,
so that route stays on the PC and is one command. A physical calculator does
not. A program can go over its cable with one command, on a G2 from Windows,
and otherwise that step is a drag in the Connectivity Kit window, with two traps
that cost an afternoon each.

```bash
hpprime install CIRCLE.hpprgm --restart     # into the emulator
hpprime pull MYPROG --diff ppl/MYPROG.txt   # and read back what it has
hpprime send programs/CIRCLE/CIRCLE.txt     # a program, to a G2 on its cable
```

The procedure for hardware by hand, and the only one for an app: open the
Connectivity Kit with the calculator connected, or with the Virtual Calculator
running; drag the `.hpprgm` file, or the whole `.hpappdir` folder, from the
file manager onto the calculator in the CK window; then `[Shift][Program]` for
a program, `[Apps]` for an app.

---

<a name="deploy.emulator-folder"></a>
## The emulator's folder really is a mailbox

| | |
|---|---|
| Identifier | `deploy.emulator-folder` |
| Kind | rule |
| Known from | emulator |

`Documents\HP Prime\Calculators\<instance>\` is the Virtual Calculator's own
file system, and it is read when the emulator starts, so a file copied into it
is installed. Three rules came out of the same session:

| | |
|---|---|
| The folder is read when the emulator starts | a file copied into a running one appears only after a restart |
| Files it does not know are left alone | a second program copied mid-session was still there, byte for byte, after a clean exit |
| It writes back | once the calculator had compiled the program, the file grew from 1,388 to 1,484 bytes: the emulator had added the compiled block, as a G2 does |

The first rule is why `install` refuses to copy into a running emulator unless
you pass `--restart`, which closes it with a window-close request rather than
a kill, so the calculator saves itself on the way out. The third is what makes
`hpprime pull` possible.

**Evidence.** Measured on 2026-09-06 on the Virtual Calculator 2.4.15515, with
a `.hpprgm` generated by `hpprime write` and copied into an idle instance
folder: it was in the Program Catalogue after launching, its source identical
to the `.txt`, and an `.hpappdir` copied the same way appeared in the
Application Library. None of this has been tried on the macOS or Linux builds;
copying works wherever the folder is found, and closing and launching the
emulator is written for Windows and says so elsewhere.

<a name="deploy.compile-once-after-a-file-copy"></a>
## A program that arrives as a file has to be compiled once

| | |
|---|---|
| Identifier | `deploy.compile-once-after-a-file-copy` |
| Kind | rule |
| Known from | emulator |

It is in the catalogue immediately and its source is right, but the exported
name is not registered until the editor's `Check` has run. Before that, Home
reads `HPKITTST` as a product of single-letter variables -- `H*P*K*I*T*T*S*T`
-- and answers 0. So, once, after a file copy:

    [Shift][Program] -> pick it -> Edit -> Check -> Esc

This is the one place where the two routes differ:
[deploy.no-manual-compile](#deploy.no-manual-compile) was measured on programs
dragged over in the Connectivity Kit, and dragging makes the calculator load
the program while copying the file into its folder does not.

**Evidence.** Measured on 2026-09-06 on the Virtual Calculator 2.4.15515:
typed on Home before compiling, 0; the editor's `Check` said *No errors in the
program*; typed on Home after, 385, the sum of squares 1..10. Nothing else
happened between those two lines. It is also why every batch of
`hpprime examples` costs three keypresses.

<a name="deploy.results-come-back-on-exit"></a>
## A matrix written by a program appears when the emulator closes

| | |
|---|---|
| Identifier | `deploy.results-come-back-on-exit` |
| Kind | rule |
| Known from | emulator |

A program that stores into a global matrix gets `M9.hpmat` written into the
calculator folder, which is how `hpprime compare` and `hpprime examples` carry
results back out.

**Evidence.** Measured 2026-09-06: `M9.hpmat` appeared at 19:51:13, the same
second as the `calc.hpsettings` write that marks the emulator closing, so the
matrix is saved on exit rather than while the program runs.

<a name="deploy.which-window-opens"></a>
## Which calculator a window opens is decided by lock files

| | |
|---|---|
| Identifier | `deploy.which-window-opens` |
| Kind | rule |
| Known from | emulator |

The emulator names its calculators `Prime`, `Prime_1`, `Prime_2` and so on,
and each window holds a lock on one of them: the first window on `Prime`, the
second on `Prime_1`. A newly launched emulator takes the first one whose lock
nobody holds, and makes the folder when it is not there, so launching the
emulator never opens a calculator with any other name, and `--calc` only says
which folder the files go into.

The locks are Qt lock files in a folder beside `Calculators` (`Temporal`, on a
Spanish install): `HPEmuInstance.lock` for `Prime`, `HPEmuInstance1.lock` for
`Prime_1`, each holding the process id of the window that has it, and gone
once that window closes. `HPPrime.exe` holds the string `Prime_%1`, which is
how the names are built. `hpprime examples` reads the locks before it launches
anything, so it knows which calculator the next window will open, and refuses
rather than open yours.

**Evidence.** Measured four ways: with `Prime` in use, a second emulator
opened `Prime_1`; with nothing running it opened `Prime`, having installed
into `Prime_1`; with a clone called `LAB` present and everything free, it
still opened `Prime`; and on 2026-09-11, with `Prime` in use and a clone
called `DOCS` free, a second emulator made an empty `Prime_1` at 19:40:31 and
opened that, leaving `DOCS` untouched. The lock behaviour was measured the
same day, when the window on `Prime` closed at 23:10:33 and its lock went with
it while `Prime_1`'s stayed, with its window's pid in it. This page used to say
a new window takes the first calculator not in use; the `DOCS` case refutes
that.

<a name="deploy.calc-hpsettings-moves"></a>
## calc.hpsettings moving says which calculator, not that the window closed

| | |
|---|---|
| Identifier | `deploy.calc-hpsettings-moves` |
| Kind | rule |
| Known from | emulator |

It is written when an emulator exits, and it is not written only then: an open
`Prime_1` rewrote it, along with its lists and matrices, three times while its
window stayed open. `hpprime compare` uses the write on exit to work out where
to send a program, and remembers the answer until the set of calculators
changes.

**Evidence.** A launch timed at 17:52:23 was preceded by a write at 17:52:22,
which was the previous emulator shutting down. The writes with the window
still open were measured on 2026-09-11 at 19:41:32, a minute after it opened,
then 20:52:55 and 23:09:22, for a reason not established.

<a name="deploy.ck-mirror"></a>
## The Connectivity Kit's folder is a mirror, not a drop box

| | |
|---|---|
| Identifier | `deploy.ck-mirror` |
| Kind | rule |
| Known from | G2 |

`Documents\HP Connectivity Kit\Calculators\<your calculator>\` is written *from*
the calculator. Leaving a file there with the CK closed installs nothing: on
connecting, the CK overwrites the folder with whatever is on the calculator,
and your file disappears.

| Route | State |
|---|---|
| Drag the file from the file manager onto the calculator in the CK | works -- this is the way |
| Drag between calculators inside the CK | works |
| Paste the text into the CK's editor | works, but it is the slow road |
| Copy the file into `Calculators\<calculator>\` | does not install: the CK overwrites it on connecting |

Nor does it always hold everything. On connecting, it held the built-in apps
and little else; the programs, lists and matrices arrived when the calculator
was expanded in the CK's tree. So a program missing from the folder is not a
program missing from the calculator.

**Evidence.** Verified the hard way on a G2 with firmware 2.4.15515: two
corrected binaries were copied there, and the emulator still opened the old
version. The files left in the folder afterwards were the ones the calculator
had written, compiled block and all. Measured on 2026-11-04 on the same
calculator: `SELFTEST.hpprgm`, installed and run, left the folder when the CK
reconnected, and came back when the tree was expanded.

<a name="deploy.content-library-send"></a>
## A physical calculator can receive a file without a drag

| | |
|---|---|
| Identifier | `deploy.content-library-send` |
| Kind | rule |
| Known from | G2 |

Copy the file into the Connectivity Kit's content library (`Contenido` on a
Spanish install), then right-click it → *Send* (`Enviar`). It is the same
destination as the drag of [deploy.ck-mirror](#deploy.ck-mirror), by a route
that does not need one window dropped onto another, which matters when the
drag is refused
([deploy.drag-refused-when-elevated](#deploy.drag-refused-when-elevated)) or
when something other than a hand is doing it.

**Evidence.** Done twice, on a G2 on firmware 2.4.15515, and verified each time
by reading the installed source back, which was identical. On 2026-09-09 with
`TAULES.hpappdir`, 409,575 characters, driven through Windows UI Automation, in
five attempts. On 2026-11-04 with `SELFTEST.hpprgm`, 1,141 characters, from
messages posted to the CK's windows: a right-click on its row and a click on the
last entry of the menu, in two attempts, the first lost when the menu closed.
The file showed in the CK's list as soon as it was copied, the mirror had it
within 3 s of the click with a compiled block, and it ran with no compile by
hand ([usb.start-by-name](usb.md#usb.start-by-name)). The same steps by hand were
not measured.

<a name="deploy.ck-offers-firmware"></a>
## The Connectivity Kit can open a firmware update with its update button focused

| | |
|---|---|
| Identifier | `deploy.ck-offers-firmware` |
| Kind | rule |
| Known from | G2 |

Once the CK has downloaded a firmware, opening it with a calculator connected can
open a window titled *Update firmware* (`Actualizar firmware`), with the update
button holding the focus. Its own text warns that the calculator's data can be
lost, and offers a backup first. The X on its title bar closes it and the
calculator keeps its firmware. A script that opens the CK has to expect this
window, and has to send no key to it. Everything measured here is on 2.4.15515, so
an update also means measuring again.

**Evidence.** Seen on 2026-11-05 with the CK 2.4 and a G2 on 20250915, offered
20260909, on the first launch after the download. Closed with a window-close
request; the calculator still reported build 15515 afterwards. Whether it opens on
every launch was not measured, and the update itself was not tried.

<a name="deploy.usb-without-the-ck"></a>
## A program can be pushed over USB without the Connectivity Kit

| | |
|---|---|
| Identifier | `deploy.usb-without-the-ck` |
| Kind | rule |
| Known from | G2 |

`hpprime send` does it, with the CK closed, on a G2 from Windows:
[usb.send-program](usb.md#usb.send-program) says what was measured and
[usb.program-message](usb.md#usb.program-message) what travels. An app has not
been tried, so for an app the drag in the CK window is the way. On the emulator
the route is [deploy.emulator-folder](#deploy.emulator-folder).

**Evidence.** Measured on 2026-11-04 on a G2 on firmware 2.4.15515: five versions
of one program, each run on the calculator afterwards. What is written about
PrimeComm, 2014, says it no longer works against current firmware; that one was
not tried.

<a name="deploy.drag-refused-when-elevated"></a>
## A drag refused with the no-entry cursor is Windows, not the file

| | |
|---|---|
| Identifier | `deploy.drag-refused-when-elevated` |
| Kind | rule |
| Known from | G2 |

The symptom is that you drag the `.hpprgm` onto the calculator, the no-entry
symbol appears and nothing happens: no dialog, no error. The ten-second check
is to drag a program the CK itself wrote; if that is refused too, the problem
is the environment. The cause found here was the Connectivity Kit having
Windows 8 compatibility mode and "run as administrator" enabled: Windows
forbids drag and drop between processes of different integrity levels (UIPI),
so the unelevated file manager cannot drop anything into an elevated window.
Clearing those two boxes makes the drag work.

Where to look: properties of the shortcut and of the `.exe`, under
*Compatibility*. The flag lives in
`HKCU\Software\Microsoft\Windows NT\CurrentVersion\AppCompatFlags\Layers` with
the executable path as the value name, but if the box is ticked on a
particular shortcut it will not appear there, and you have to look at the
`.lnk` you actually launch it from, which need not be the one on the desktop.

**Evidence.** Diagnosed and fixed on the machine this documentation is written on,
with a G2 connected.

<a name="deploy.no-manual-compile"></a>
## A program dragged over runs without compiling it by hand

| | |
|---|---|
| Identifier | `deploy.no-manual-compile` |
| Kind | rule |
| Known from | G2 |

Type its name on Home, or open it from the catalogue. A very large program may
need an explicit compile before it will run -- that is reported, not measured,
and the compile action is in the Program Catalogue. If it happens to you it is
worth reporting, because it would mean there is a size at which this stops
holding.

**Evidence.** Measured on a G2 with firmware 2.4.15515, with half a dozen
programs transferred and run in one sitting, none of them compiled by hand
first. The file-copy route is different:
[deploy.compile-once-after-a-file-copy](#deploy.compile-once-after-a-file-copy).

<a name="deploy.read-it-back"></a>
## Do not trust that you installed it: read it back

| | |
|---|---|
| Identifier | `deploy.read-it-back` |
| Kind | rule |
| Known from | G2 |

The source can be pulled out of the installed binary and compared with your
repository. On the emulator that is one command, and it exits 1 if they
differ, so it works as a gate in a script. For a physical calculator, the same
thing over the CK mirror, which is a mirror of what the calculator holds and
therefore fine to read:

```bash
hpprime read ".../Calculators/HP Prime/MYPROG.hpprgm" -o installed.txt
diff installed.txt ppl/MYPROG.txt
```

Fixing something on the PC and forgetting to send it over is how an installed
app ends up two commits behind the code you were trusting.

**Evidence.** The round trip is verified byte for byte in
[formats.container](formats.md#formats.container); this fact is the habit that
uses it, and it is how a two-commit drift was actually found here.

<a name="deploy.writer-on-hardware"></a>
## A program generated on the PC runs on a G2

| | |
|---|---|
| Identifier | `deploy.writer-on-hardware` |
| Kind | rule |
| Known from | G2 |

A program with a template's header and the source put in by `hpprime write`, never
touched by the CK or by the calculator, has been loaded, compiled and run on
an HP Prime G2. Twice: once with a template taken from the machine it was
built on, and once with `templates/code.hpprgm`, the one this repository
ships, which is the file you get when you clone.

| | |
|---|---|
| What was generated | 3,326 bytes, no compiled block |
| The source inside | identical to the original `.txt` |
| `SELF1` (sum of squares 1..10) | 385 |
| `SELF2` (an accented string) | `writer OK - àèóç - 4242`, accents intact |
| `SELF3` (checks both internally) | 1 |

Type `SELF3`, not `SELF3()`:
[ppl.home-no-parentheses](ppl.md#ppl.home-no-parentheses).

**Evidence.** Measured on a G2 with firmware 2.4.15515. The calculator adds
its own compiled block when it loads a program, so the program being accepted
says it was understood, and `SELF3` verifies inside the calculator that the
loop sums to 385 and that the accented string is 23 characters long. The test
program is in `examples/selftest/`, so the experiment can be repeated with
`hpprime write examples/selftest/SELFTEST.txt -o SELFTEST.hpprgm`.

<a name="deploy.template-from-the-ck"></a>
## A template is a program the Connectivity Kit wrote, and the mirror has almost none

| | |
|---|---|
| Identifier | `deploy.template-from-the-ck` |
| Kind | rule |
| Known from | G2 |

A template is a code `.hpprgm` with no compiled block, its source starting at
offset 152 ([formats.source-offset-152](formats.md#formats.source-offset-152)).
One ships at `templates/code.hpprgm` and every tool picks it up on its
own, so you only need your own if that one ever fails you.

What does not work is assuming there are some in the CK mirror: everything in
it has been through the calculator, and the calculator adds its compiled block
to everything it saves. The reliable way to make one is to create a new
program inside the Connectivity Kit itself (right click → *New* on *Program*),
write two lines that compile, and copy it out of the mirror folder before
sending it to the calculator.

**Evidence.** Measured on one machine: of 58 program containers in the mirror,
2 were usable as templates, and both were `.hpappprgm` files from apps.
`hpprime templates` applies the test, and `hpprime write` refuses a template
with a compiled block, so the mistake cannot slip through silently.

<a name="deploy.which-calculator-is-which"></a>
## Which calculator a mirror folder belongs to is in its settings file

| | |
|---|---|
| Identifier | `deploy.which-calculator-is-which` |
| Kind | rule |
| Known from | G2 |

When there are several folders under `Calculators\`, the `settings` file in
each one carries its identifier, which for a physical calculator is its serial
number. The folder name is whatever the CK shows in its tree. A mirror folder
is only populated once the CK has actually talked to that calculator, so
finding it empty does not mean anything is broken.

**Evidence.** Read from the mirrors of the calculators on this machine, one of
them a G2 with firmware 2.4.15515.
